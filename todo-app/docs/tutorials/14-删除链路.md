## 一、链路总览

```
点「删除」
  → ElMessageBox.confirm(...)
  → 点「取消」：return，不发请求
  → 点「删除」：deleteTask(row.id)
  → axios：DELETE /api/tasks/9
  → Vite / Nginx 把 /api 转到 backend:8080
  → TaskController.delete：removeTask(id)
  → TaskServiceImpl.removeTask：removeById + clearStatsCache
  → @TableLogic 把 DELETE 改写成 UPDATE deleted=1
  → Result.ok()  { code:200, data:null }
  → 本页最后一条？pageNum -= 1
  → loadAll()
  → 列表少一行、分页和统计更新
```

## 二、前端：先确认，再删除

`TodoView.vue:237-260`（节选）：

```js
async function handleDelete(row) { // 点“删除”时执行
  try {
    await ElMessageBox.confirm(`确定要删除任务「${row.title}」吗？`, '删除确认') // 点“删除”才继续
  } catch {
    return // 点“取消”会进 catch，直接结束，不发 DELETE
  }

  try {
    await deleteTask(row.id) // 发 DELETE 请求
    ElMessage.success('删除成功') // 成功提示
    if (list.value.length === 1 && query.pageNum > 1) { // 删的是本页最后一条
      query.pageNum -= 1 // 页码回退，避免空白页
    }
    await loadAll() // 重新查列表和统计
  } catch (e) { // 失败时拦截器已提示
  }
}
```

- **做什么**：二次确认 → 删除 → 页码回退 → 刷新。
- **为什么**：
  - 删除是破坏性操作，先确认，防止误点。
  - 删除本页最后一条后，这一页会空；页码回退一页能看到前面的数据。
  - 删除成功后重新查，前端不自己从数组里删，避免分页/统计错乱。

## 三、请求：DELETE

`api/task.js:77-79`：

```js
export function deleteTask(id) { // 删除接口封装
  return request.delete(`/tasks/${id}`) // DELETE /api/tasks/{id}；没有请求体
}
```

- **做什么**：把 id 拼到 URL，发 DELETE。
- **为什么**：REST 用 URL 定位资源、用 DELETE 表示删除；id 在路径里，不需要请求体。

请求路径：

```text
deleteTask(row.id)
  → request.delete(`/tasks/${id}`) // axios 方法
  → DELETE /api/tasks/9            // baseURL '/api' + '/tasks/9'
  → 浏览器发到 5173 / 8081
  → Vite / Nginx 匹配 /api
  → http://backend:8080/api/tasks/9
  → TaskController.delete
```

- **做什么**：经过代理到达后端。
- **为什么**：浏览器只访问前端端口，代理负责转发，避免跨域和写死地址。

## 四、后端 Controller：成功 true，失败 404

`TaskController.java:168-177`：

```java
@DeleteMapping("/{id}") // 处理 DELETE /api/tasks/{id}
public Result<Void> delete(@PathVariable Long id) { // id 来自 URL
    if (!taskService.removeTask(id)) { // false=不存在/已删
        return Result.fail(404, "任务不存在"); // 返回业务 404
    }
    return Result.ok(); // 删除成功，data 为 null
}
```

- **做什么**：调用 Service，根据返回值决定 404 还是成功。
- **为什么**：
  - `removeTask` 返回 `true/false`，Controller 不用再查一次。
  - 删除成功没有数据要返回，所以用 `Result.ok()`，`data=null`。

## 五、后端 Service：`removeById` + 清缓存

`TaskServiceImpl.java:235-242`：

```java
@Transactional(rollbackFor = Exception.class) // 出异常回滚
public boolean removeTask(Long id) { // true=删成功，false=不存在
    boolean removed = this.removeById(id); // 实际是 UPDATE deleted=1
    clearStatsCache(); // 统计变了，删缓存
    return removed; // 把结果交给 Controller
}
```

- **做什么**：删除记录，清统计缓存。
- **为什么**：
  - `removeById` 看起来像 DELETE，但因为 `@TableLogic`，实际是逻辑删除。
  - 统计数字会变，必须删缓存，否则统计卡片最多 60 秒还是旧值。
  - 返回布尔值，Controller 才能区分“删到了”和“不存在”。

`TaskServiceImpl.java:290-298`：

```java
private void clearStatsCache() { // 删除统计缓存
    try {
        redisTemplate.delete(STATS_KEY); // DEL todo:stats
    } catch (Exception e) {
        log.warn("清除 Redis 缓存失败：{}", e.getMessage()); // 缓存失败不影响业务
    }
}
```

- **做什么**：删除 Redis 统计缓存。
- **为什么**：缓存是加速层，Redis 挂了也要让删除成功；下次读统计会重新查数据库。

## 六、实体和配置：为什么是 UPDATE 不是 DELETE

`Task.java:104-106`：

```java
@TableLogic // 告诉 MyBatis-Plus：这是逻辑删除字段
@JsonIgnore // 不要返回给前端
private Integer deleted; // 0=正常，1=已删除
```

- **做什么**：声明逻辑删除字段。
- **为什么**：数据不真删，方便追溯；查询自动加 `deleted=0`，删除自动改成 `UPDATE`。

`application.yml:49-52`：

```yaml
mybatis-plus:
  global-config:
    db-config:
      logic-delete-field: deleted # 逻辑删除字段名
      logic-delete-value: 1       # 已删除的值
      logic-not-delete-value: 0   # 未删除的值
```

- **做什么**：配置逻辑删除的字段和取值。
- **为什么**：告诉框架 `deleted=1` 表示删除，生成 SQL 时自动使用。

实际 SQL：

```sql
UPDATE t_task                   -- 任务表
SET deleted = 1                 -- 标记删除，不是真删
WHERE id = ? AND deleted = 0;   -- 只删还没删过的
```

- **做什么**：把 `deleted` 从 0 改成 1。
- **为什么**：
  - 记录还在表里，可以通过 `UPDATE deleted=0` 恢复。
  - 查询自动过滤 `deleted=1`，所以列表看不到。
  - `WHERE deleted=0` 防止重复删除。

## 七、返回和回显

`Result.java:42-59`：

```java
public static <T> Result<T> ok(T data) { // 成功响应
    Result<T> result = new Result<>();
    result.setCode(200);       // 业务成功
    result.setMessage("成功"); // 提示
    result.setData(data);      // 删除没有数据，data=null
    return result;
}
```

- **做什么**：包装成功响应。
- **为什么**：所有接口结构一致，前端拦截器统一处理。

响应：

```json
{ "code": 200, "message": "成功", "data": null }
```

| 字段 | 意思 |
|---|---|
| `code` | 200 表示删除成功 |
| `message` | 提示文字 |
| `data` | 删除没有返回数据，所以是 `null` |

回显：

```js
await loadAll() // 重新查列表和统计
```

- **做什么**：重新加载列表和统计。
- **为什么**：
  - 列表查询带 `deleted=0`，被删的行不再返回。
  - `total` 减少，分页页数可能变化。
  - 统计重新 `COUNT`，数字减少。
  - 缓存被删，这次统计是“回源”，下次刷新才“命中”（统计逻辑见 [11 查询链路](11-查询链路.md) §十）。

## 九、常见坑

| 现象 | 原因 |
|---|---|
| 点删除没反应 | 确认框被取消，或 `catch` 吞了 |
| 第二次删同一条返回 404 | 已经逻辑删除，`WHERE deleted=0` 匹配不到 |
| 数据库里还能查到 | 逻辑删除不是物理删除，看 `deleted` 字段 |
| 删完当前页空白 | 没做页码回退 |
