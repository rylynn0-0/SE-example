## 一、两个入口，两条接口

| 入口 | 改什么 | HTTP | 为什么用这个 |
|---|---|---|---|
| 编辑弹窗 → 保存 | 标题、备注、优先级、日期 | `PUT /api/tasks/{id}` | 提交的是编辑表单的完整字段 |
| 行内开关 | 只改 `finished` | `PATCH /api/tasks/{id}/finished` | 只改一个字段，属于局部更新 |

```
编辑：
点「编辑」→ openEdit(row) 回填 form → 点「保存」
→ PUT /api/tasks/{id} → Controller.update → Service.updateTask
→ UPDATE ... WHERE id=? AND deleted=0 → loadAll → 行更新

开关：
点开关 → handleToggle(row)
→ PATCH /api/tasks/{id}/finished → Controller.toggle → Service.toggleFinished
→ getById → 取反 → updateById → loadAll → 开关/统计/排序更新
```

两个请求都走 `request` 这个 axios 实例，再经 Vite/Nginx 把 `/api` 转到 8080。

## 二、编辑弹窗：回填

`TodoView.vue:192-202`：

```js
function openEdit(row) { // row 是表格里当前行的数据
  dialog.id = row.id // 记住编辑哪条；有 id 就是编辑模式
  Object.assign(form, { // 把当前行数据复制到表单
    title: row.title,                   // 标题
    description: row.description ?? '', // 备注；null 用空串
    priority: row.priority ?? 2,        // 优先级；null 默认中
    dueDate: row.dueDate ?? null        // 日期；null 保持 null
  })
  dialog.visible = true // 打开弹窗
}
```

- **做什么**：把当前行的数据填进表单，打开弹窗。
- **为什么**：
  - 列表接口返回的是完整 `Task`，`row` 里已经有编辑需要的字段，**不用再发 `GET /api/tasks/{id}`**。
  - `??` 处理 `null`，避免把 `null` 直接塞进输入框显示异常。

## 三、编辑保存：发 PUT

`TodoView.vue:216-218`：

```js
if (dialog.id) { // 有 id 才是编辑
  await updateTask(dialog.id, { ...form }) // 把 id 和表单发给后端
  ElMessage.success('修改成功') // 成功提示
}
```

- **做什么**：调用更新接口。
- **为什么**：`dialog.id` 是新增/编辑的分支开关；新增时它是 `null`，不会走这里。

`api/task.js:53-55`：

```js
export function updateTask(id, data) { // 更新接口封装
  return request.put(`/tasks/${id}`, data) // PUT /api/tasks/{id}
}
```

- **做什么**：把 id 拼进 URL，表单作为请求体。
- **为什么**：REST 用 URL 表示资源、用方法表示动作；`PUT` 语义是“更新这个资源”。

请求体：

```json
{
  "title": "完成软工课程设计开题报告（已改期）",
  "description": "整理论文选题",
  "priority": 3,
  "dueDate": "2026-11-20"
}
```

| 字段 | 意思 |
|---|---|
| `title` | 标题，必填 |
| `description` | 备注；传 `null` 可以清空 |
| `priority` | 1 低 / 2 中 / 3 高 |
| `dueDate` | 截止日期；传 `null` 可以清空 |

## 四、后端 Controller：先查存在，再更新

`TaskController.java:121-135`：

```java
@PutMapping("/{id}") // 处理 PUT /api/tasks/{id}
public Result<Task> update(@PathVariable Long id, @RequestBody Task task) { // id 来自 URL，task 来自 JSON
    if (!StringUtils.hasText(task.getTitle())) { // 标题不能为空
        return Result.fail(400, "任务标题不能为空"); // 业务失败
    }
    if (taskService.getById(id) == null) { // 先确认任务存在
        return Result.fail(404, "任务不存在"); // 不存在返回 404
    }
    return Result.ok(taskService.updateTask(id, task)); // 更新并返回
}
```

- **做什么**：校验标题、检查 id、调用 Service。
- **为什么**：
  - 标题仍要必填，不能通过编辑接口把标题清空。
  - 先查存在，避免“更新 0 行但返回成功”的假成功。
  - `@PathVariable` 取 URL 的 id，`@RequestBody` 取 JSON 字段。

## 五、后端 Service：更新、清缓存、回查

`TaskServiceImpl.java:207-223`：

```java
@Transactional(rollbackFor = Exception.class) // 出异常回滚
public Task updateTask(Long id, Task task) { // 返回更新后的任务
    task.setId(id); // 以 URL 的 id 为准
    task.setDeleted(null); // 不允许改逻辑删除标记
    this.updateById(task); // UPDATE ... WHERE id=? AND deleted=0
    clearStatsCache(); // 统计可能变，删缓存
    return this.getById(id); // 返回数据库最新数据
}
```

- **做什么**：把请求体字段更新到数据库。
- **为什么**：
  - `setId(id)` 防止有人把请求体里的 id 改成别的任务。
  - `setDeleted(null)` 防止通过编辑接口改逻辑删除标记。
  - 写操作清统计缓存，否则统计卡片可能还是旧数字（`clearStatsCache` 代码见 [12 新增链路](12-新增链路.md) §七）。
  - 回查保证返回 `update_time` 等数据库生成的值。

## 六、实体字段策略：为什么备注和日期能清空

`Task.java:57、75`：

```java
@TableField(updateStrategy = FieldStrategy.ALWAYS) // 即使值是 null 也写进 UPDATE
private String description; // 备注

@TableField(updateStrategy = FieldStrategy.ALWAYS)
@JsonFormat(pattern = "yyyy-MM-dd")
private LocalDate dueDate; // 截止日期
```

- **做什么**：允许备注/日期被更新为 `null`。
- **为什么**：MyBatis-Plus 默认跳过 `null` 字段；用户清空备注时传 `null`，不加 `ALWAYS` 的话旧值永远删不掉。

编辑 SQL：

```sql
UPDATE t_task                   -- 任务表
SET title=?,                    -- 新标题
    description=?,              -- 新备注；传 null 也能清空
    priority=?,                 -- 新优先级
    due_date=?                  -- 新日期；传 null 也能清空
WHERE id=? AND deleted=0;       -- 只更新未删除的这条
```

- **做什么**：更新这条任务的字段。
- **为什么**：`WHERE deleted=0` 由 `@TableLogic` 自动加，已删除的任务不会被编辑。

## 八、状态开关：模板

`TodoView.vue:374`：

```vue
<el-switch :model-value="row.finished === 1" @change="handleToggle(row)" /> <!-- 只读后端状态；拨动时调 handleToggle -->
```

- **做什么**：显示完成状态，用户拨动时触发函数。
- **为什么**：用 `:model-value` 而不是 `v-model`，开关不会“抢跑”。
  如果后端失败，`row.finished` 没变，开关保持原样，不会出现“页面成功、数据库失败”。

## 九、状态开关：发 PATCH

`TodoView.vue:271-278`：

```js
async function handleToggle(row) { // 点开关时执行
  try {
    await toggleTask(row.id) // PATCH /api/tasks/{id}/finished
    await loadAll() // 成功后重新查，开关以后端为准
  } catch (e) { // 失败时拦截器已提示
  }
}
```

- **做什么**：请求切换状态，成功后刷新。
- **为什么**：页面不手动改 `row.finished`；成功后重新查，状态、统计、排序都会自动更新。

`api/task.js:65-67`：

```js
export function toggleTask(id) { // 切换完成状态
  return request.patch(`/tasks/${id}/finished`) // PATCH，不需要请求体
}
```

- **做什么**：调用局部更新接口。
- **为什么**：只改 `finished` 一个字段，用 `PATCH` 比 `PUT` 语义更准确。

## 十、状态开关：后端

`TaskController.java:147-157`：

```java
@PatchMapping("/{id}/finished") // 处理 PATCH /api/tasks/{id}/finished
public Result<Task> toggle(@PathVariable Long id) { // id 来自 URL
    Task task = taskService.toggleFinished(id); // 让 Service 取反
    if (task == null) { // 任务不存在
        return Result.fail(404, "任务不存在");
    }
    return Result.ok(task); // 返回切换后的任务
}
```

- **做什么**：接收 id，调用 Service，处理 404。
- **为什么**：Controller 不写“取反”逻辑，业务规则统一放 Service。

`TaskServiceImpl.java:254-273`：

```java
@Transactional(rollbackFor = Exception.class) // 出异常回滚
public Task toggleFinished(Long id) { // 返回切换后的任务
    Task task = this.getById(id); // 先查当前值
    if (task == null) return null; // 不存在，交给 Controller 返 404

    task.setFinished(task.getFinished() != null && task.getFinished() == 1 ? 0 : 1); // 1→0，其它→1
    this.updateById(task); // 写回数据库
    clearStatsCache(); // 完成数变了，删统计缓存
    return this.getById(id); // 返回最新数据
}
```

- **做什么**：查当前值、取反、更新、清缓存。
- **为什么**：
  - 先查再取反，比前端传新状态更安全（前端可能传错）。
  - 条件里判断 `!= null`，兼容脏数据。
  - 完成数量变了，统计缓存必须失效。

核心 SQL：

```sql
UPDATE t_task
SET finished=?              -- 新的完成状态：0 或 1
WHERE id=? AND deleted=0;   -- 只改未删除的这条
```

- **做什么**：更新完成状态。
- **为什么**：`WHERE deleted=0` 防止改到已删除数据；只更新这一条。

> 因为 Service 是“先查完整实体，再 `updateById`”，日志里的 `SET` 可能还会带上
> `title`、`description` 等原值。业务结果没问题，只是 SQL 比“只改 finished”宽一点。

- **做什么**：重新加载列表和统计。

## 十二、统一响应：成功和失败长什么样

`Result.java:42-59、68-85`（简化）：

```java
public static <T> Result<T> ok(T data) { // 成功响应
    Result<T> result = new Result<>();
    result.setCode(200); // 业务成功
    result.setMessage("成功"); // 提示
    result.setData(data); // 更新后的任务
    return result;
}

public static <T> Result<T> fail(Integer code, String message) { // 失败响应
    Result<T> result = new Result<>();
    result.setCode(code); // 400 或 404
    result.setMessage(message); // 给前端看的提示
    return result; // data 保持 null
}
```

- **做什么**：把成功/失败都包成 `{ code, message, data }`。
- **为什么**：前端拦截器只需判断 `code`，不用区分不同接口的返回格式。

## 十四、常见坑

| 现象 | 原因 |
|---|---|
| 编辑弹窗是空的 | `openEdit(row)` 没拿到 `row`，或列表没返回字段 |
| 备注/日期清不掉 | 字段没加 `FieldStrategy.ALWAYS` |
| 开关点完弹回 | 请求失败，或没有重新 `loadAll` |
| 405 | 用 PUT 调了 PATCH 接口，或反过来 |
