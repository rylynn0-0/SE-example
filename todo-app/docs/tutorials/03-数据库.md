# 03 · 数据库：MySQL 与 Redis

> 一句话：**MySQL 存「真相」，Redis 存「缓存」**。MySQL 数据丢了是事故，Redis 数据丢了只是变慢。

> 配套手册：建表脚本怎么写、SQL 语法，见 [09 数据库模板](09-数据库模板.md)。

## 二、关系型数据库：七个词

| 概念 | 含义 | 本项目 |
|---|---|---|
| 库 database | 一组表的集合 | `todo_db` |
| 表 table | 一类数据 | `t_task` |
| 列 column | 字段 + 类型 + 约束 | `title VARCHAR(100)` |
| 行 row | 一条记录 | 一条任务 |
| 主键 primary key | 唯一标识一行 | `id` |
| 索引 index | 加速查询的结构 | `idx_finished`、`idx_title` |
| 事务 transaction | 一组操作要么全成功要么全失败 | `@Transactional` |

## 三、`t_task` 表：每一列为什么这么设计

打开 `backend/src/main/resources/db/init.sql`：

```sql
CREATE TABLE t_task
(
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键 ID',
    title       VARCHAR(100)    NOT NULL COMMENT '任务标题',
    description VARCHAR(500)             DEFAULT NULL COMMENT '任务备注',
    priority    TINYINT         NOT NULL DEFAULT 1 COMMENT '优先级：1低 2中 3高',
    finished    TINYINT         NOT NULL DEFAULT 0 COMMENT '完成状态：0未完成 1已完成',
    due_date    DATE                     DEFAULT NULL COMMENT '截止日期',
    create_time DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    update_time DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP
                                 ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    deleted     TINYINT         NOT NULL DEFAULT 0 COMMENT '逻辑删除：0未删除 1已删除',
    PRIMARY KEY (id),
    KEY idx_finished (finished),
    KEY idx_title (title)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

### 设计点 1：类型要「刚好够用」

| 用途 | 类型 | 为什么 |
|---|---|---|
| 主键 | `BIGINT` | 比 `INT` 留更多余量，将来数据量涨了不用改表 |
| 短文本 | `VARCHAR(100)` | 标题限长，避免有人塞一篇作文 |
| 布尔/小枚举 | `TINYINT` | `TINYINT` 占 1 字节；`Boolean` 在 MySQL 里其实也是它 |
| 日期 | `DATE` | 截止日只要年月日，不要时间 |
| 日期时间 | `DATETIME` | 创建/更新时间 |

> 金额绝不要用 `FLOAT/DOUBLE`（`0.1 + 0.2 != 0.3`），要用 `DECIMAL`。本项目没有金额字段，但记住这条。

### 设计点 2：时间交给数据库维护

```sql
create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

| 场景 | 行为 |
|---|---|
| 插入时 Java 不传时间 | 数据库填 `CURRENT_TIMESTAMP` |
| 更新任意列 | `update_time` 自动刷新 |

为什么不让 Java 赋值？因为绕过接口直接改库、或用定时任务写入时，时间就不准了。放在数据库层，**任何入口都一致**。

### 设计点 3：两个索引对应两种查询

```sql
KEY idx_finished (finished),   -- 状态筛选 + 排序
KEY idx_title (title)          -- 关键词搜索
```

什么时候加索引：经常出现在 `WHERE`、`ORDER BY`、`JOIN` 里的列。
代价：写入变慢（每次 INSERT 要维护索引）、占磁盘。所以不是越多越好。

**关于标题索引的一个诚实说明**：本项目用的是 `LIKE '%关键词%'`，

```sql
WHERE title LIKE '%报告%'    -- 前面有 %，索引失效，全表扫描
WHERE title LIKE '报告%'     -- 能用索引
```

数据量小（8 条）无所谓；真到百万行要考虑全文索引或搜索引擎。

### 设计点 4：逻辑删除

```sql
deleted TINYINT NOT NULL DEFAULT 0
```

删除时不 `DELETE`，而是 `UPDATE t_task SET deleted = 1`。
好处：数据可追溯、可恢复；代价：所有查询都要记得过滤 `deleted = 0`。

本项目把「过滤」这件事交给了 MyBatis-Plus 的 `@TableLogic` 自动完成 —— 详见 [05 后端与数据库耦合](05-后端与数据库耦合.md)。

### 设计点 5：字符集必须 `utf8mb4`

```sql
DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci
```

MySQL 里的 `utf8` 是**三字节**的，存不了 emoji 和部分生僻字；`utf8mb4` 才是完整的四字节 UTF-8。

## 四、会写这几条 SQL 就够了

```sql
-- 增
INSERT INTO t_task (title, priority) VALUES ('学习 MySQL', 2);

-- 查：分页 + 排序（模拟后端的分页查询）
SELECT * FROM t_task
WHERE deleted = 0 AND title LIKE '%报告%' AND finished = 0
ORDER BY finished ASC, priority DESC, id DESC
LIMIT 0, 5;

-- 改
UPDATE t_task SET finished = 1 WHERE id = 1;

-- 删（物理删，不推荐）
DELETE FROM t_task WHERE id = 1;

-- 删（逻辑删，本项目用这种）
UPDATE t_task SET deleted = 1 WHERE id = 1;
```

`LIMIT offset, size`：跳过 offset 条，取 size 条。
第 1 页是 `LIMIT 0,5`，第 2 页是 `LIMIT 5,5`。

**查看执行计划**（判断有没有走索引）：

```sql
EXPLAIN SELECT * FROM t_task WHERE finished = 0;
```

## 五、数据是怎么进去的

```
init.sql 挂载到 MySQL 容器的 /docker-entrypoint-initdb.d/
   ↓
MySQL 首次启动（数据目录为空）时自动执行
   ↓
建库 todo_db + 建表 t_task + 插入 8 条演示数据
```

**只在首次执行**。这是新手最常困惑的点：

| 操作 | init.sql 会执行吗 |
|---|---|
| 第一次 `docker compose up` | ✅ 执行 |
| 再次 `up` | ❌ 数据卷已存在，跳过 |
| `down` 后再 `up` | ❌ 卷还在 |
| `down -v` 后再 `up` | ✅ 卷被删了，重新执行 |

改了 `init.sql` 想生效，必须：

```bash
docker compose down -v
docker compose up -d
```

演示数据用相对日期生成，比如 `DATE_ADD(CURDATE(), INTERVAL 2 DAY)`（今天 + 2 天），这样任何时候打开都有「紧迫感」，不会全部过期。

## 六、Redis：为什么还要一个数据库

Redis 是**内存**里的键值数据库：

```
GET todo:stats  →  {"total":8,"finished":3,"unfinished":5}
```

| 对比 | MySQL | Redis |
|---|---|---|
| 存储位置 | 磁盘 | 内存 |
| 速度 | 毫秒级 | 微秒级 |
| 数据结构 | 表 / 行 / 列 | key-value（String/Hash/List/Set/ZSet） |
| 持久化 | 天然持久 | 可选（RDB/AOF），但**不作为权威数据源** |
| 定位 | 真相 | 加速 |

它常见的四种用途：

| 用途 | 说明 |
|---|---|
| **缓存**（本项目） | 挡住高频读 |
| 分布式锁 | `SETNX` + 过期时间 |
| 计数器 | `INCR`，浏览量、点赞数 |
| Session 共享 | 多台服务器共享登录态 |

## 七、Redis 的三个概念

### 7.1 key 的命名

```java
redisTemplate.opsForValue().set("todo:stats", json);
```

规范是 `业务:对象:标识`，用冒号分层：

| 好 | 差 |
|---|---|
| `todo:stats` | `s` |
| `user:1001:profile` | `user1001profile` |

好处是能按业务批量查/删：`redis-cli KEYS "todo:*"`。

### 7.2 TTL（过期时间）

```java
redisTemplate.opsForValue().set(key, value, 60, TimeUnit.SECONDS);
```

为什么必须设过期时间：不设就永不过期，一旦数据源变了，缓存就永远是错的。**TTL 是「最终一致性」的兜底。**

### 7.3 Cache-Aside（旁路缓存）

最经典的缓存模式，本项目采用：

```
读：
  1. 查缓存 → 命中 → 直接返回
  2. 未命中 → 查数据库
  3. 把结果写回缓存（带 TTL）
  4. 返回

写：
  1. 改数据库
  2. 删除缓存（注意：是删除，不是更新）
```

**为什么写操作是「删除」而不是「更新」缓存？**

两个请求并发更新时，A 先写库、B 后写库，但 B 先更新缓存、A 后更新缓存 → 缓存里是旧值，数据库里是新值，长期不一致。
删除缓存则不同：下次谁来读，谁就从数据库重新取，天然拿到最新值。

## 八、本项目的缓存设计（先懂设计，代码在 05）

Redis 全项目**只有一个落点**：统计接口。刻意做小，但把完整流程走通了。

### 8.1 缓存什么

```java
long total = this.count();                                              // 总数
long finished = this.count(new LambdaQueryWrapper<Task>().eq(Task::getFinished, 1));  // 已完成
```

每次请求统计都要执行**两次 `COUNT(*)`**（全表扫描），而统计数字的变化频率远低于读取频率 —— 典型的「读多写少」，最适合缓存。

### 8.2 三个参数

| 参数 | 值 | 为什么 |
|---|---|---|
| key | `todo:stats` | 业务:对象 命名 |
| 过期时间 | 60 秒 | 短一点，便于演示「过期后重新回源」 |
| 内容 | `TaskStats` 的 JSON | 总数 / 已完成 / 未完成 |

### 8.3 为什么返回值里带 `fromCache` 和 `ttl`

纯技术的缓存是「隐形」的，界面看不出它到底有没有生效。
本项目让接口多返回两个字段：

```json
{ "total": 8, "finished": 3, "unfinished": 5, "fromCache": true, "ttl": 42 }
```

前端据此显示「Redis 命中 · 剩余 42s」还是「Redis 回源」—— 刷新页面就能肉眼看到缓存生效，答辩演示特别好用。

## 九、命令行验证 + 实验

先访问一次统计接口（让缓存写进去）：

```bash
curl http://localhost:8080/api/tasks/stats
```

再去看 Redis：

```bash
docker exec -it todo-redis redis-cli GET todo:stats
docker exec -it todo-redis redis-cli TTL todo:stats     # 剩余秒数
docker exec -it todo-redis redis-cli KEYS "todo:*"
```

**实验 1：手动删缓存**

```bash
docker exec -it todo-redis redis-cli DEL todo:stats
```

再刷新页面 → 标签从「Redis 命中」变回「Redis 回源」。
说明：只要 key 不在，下次读就会去查数据库并重新写回。

**实验 2：等它自然过期**

访问一次统计，然后等 60 秒再访问 —— `fromCache` 会变回 `false`。
说明 TTL 起到了兜底作用。

## 十、自测：能不能答上来

1. `BIGINT` 和 `INT` 做主键有什么区别？
2. `create_time` 和 `update_time` 是谁维护的？
3. `LIKE '%报告%'` 能不能用上 `idx_title`？
4. 逻辑删除和物理删除各有什么代价？
5. 为什么本项目只缓存统计，不缓存任务列表？
6. 写操作为什么删缓存而不是更新缓存？

<details>
<summary>参考答案</summary>

1. `BIGINT` 范围大得多，数据量增长后不用改表；`INT` 约 21 亿上限。
2. 数据库：`DEFAULT CURRENT_TIMESTAMP` 和 `ON UPDATE CURRENT_TIMESTAMP`。
3. 不能（前面有 `%`），会全表扫描；`'报告%'` 才能用。
4. 逻辑删除：数据可追溯，但每条查询都要带 `deleted=0`、索引变大；物理删除：干净，但不可恢复。
5. 统计是两次全表 `COUNT` 且读多写少；列表查询条件多变、结果集大，缓存命中率低、失效复杂。
6. 并发更新时「更新缓存」可能用旧值覆盖新值；删除缓存让下次读强制回源，更安全。

</details>

## 十一、常见错误

| 现象 | 原因 | 解决 |
|---|---|---|
| `Communications link failure` | 后端比 MySQL 先起来 | 等健康检查通过，或重启后端 |
| `Access denied for user` | 账号密码不对 | 对照 compose 里的 `MYSQL_USER/PASSWORD` |
| `Unknown database 'todo_db'` | 库没建 | 检查 `MYSQL_DATABASE` 或 init.sql |
| `Table 'todo_db.t_task' doesn't exist` | init.sql 没执行 | `docker compose down -v` 后重建 |
| 中文乱码 | 字符集不是 utf8mb4 | 建库/建表/JDBC 三处都设 |
| 时间差 8 小时 | 时区不一致 | 容器 `TZ` + JDBC `serverTimezone` |
| 改了 init.sql 没生效 | 数据卷已存在 | `down -v` |
| 统计数字不刷新 | 缓存没失效（60 秒内） | 等过期或 `DEL todo:stats` |

> 中文乱码还有一个隐蔽原因：容器内 `LANG` 未设置时，mysql 客户端默认 latin1，
> 执行 init.sql 会把中文写成「å®Œæˆ」这种双重编码。本项目用 `SET NAMES utf8mb4;` + `LANG=C.UTF-8` 解决了。
